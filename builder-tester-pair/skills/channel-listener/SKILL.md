# channel-listener

Turns the current session into a poller. Each tick reads new items since a stored watermark, decides
whether each one is **in scope**, and acts only on those. Nothing is deployed: the listener lives exactly
as long as the session that started it; its state on disk survives, so the next session catches up.

The config is generated by `setup-pair render` from `pair.yaml` into
`~/.claude/channel-listener/config.json`. Do not hand-edit it on a pair's workspace — change `pair.yaml`
(or the template) and render again.

## Why polling and not a real event subscription

Chat services are reachable **only through MCP tools**, which only the agent can call — not a shell
script or a background process. A push design would need a chat app or bot, which is a deployment. So
`/loop` driving one tick at a time is the mechanism.

## Modes

Invoke as `/channel-listener <mode>`:

| Mode | Action |
|---|---|
| `init` | Seed every watermark to *now* (so the first tick does not replay history), print the loop command |
| `tick` | One poll cycle (this is what `/loop` calls) |
| `status` | Show config, watermarks, and what was seen last tick |
| `stop` | Tell the user to end the loop; leave state intact for resume |
| *(none)* | If state exists → `tick`; else → `init` |

## Continuous operation

```
/loop <schedule.tick_minutes>m /channel-listener tick
```

The pair's start command sets this up and makes sure exactly one such loop exists.

## Before the first tick: resolve the tool names

MCP tool names are per install (`mcp__<server>__<tool>`), and several hubs may expose the same family
with different behaviour. List your tools and find the real names for `microsoft_list_channel_messages`,
`microsoft_list_chat_messages`, `microsoft_list_chats`, `slack_read_channel`, and the Jira list tool. If
a family resolves on more than one hub, test each with one read and use the one that returns data.
**A `null` or "account not found" from one hub is not evidence that no account exists** — try the other
hub before concluding anything. If nothing resolves, stop and ask the owner: a wrong prefix is
indistinguishable from a missing tool.

Slack channel search defaults to public channels only: pass `channel_types: "public_channel,private_channel"`
or a private channel looks like it does not exist.

## Config — `~/.claude/channel-listener/config.json`

| Key | What it holds |
|---|---|
| `sources` | One object per thing to read (kinds below) |
| `scope` | Per app: `aliases`, `repos`, `services`, `infra`, `tickets` (regex) |
| `prefilter` | Loose regex, stage-1 noise cut |
| `identities` | Who "self" is on Teams/Slack and the bot-prefix self-filter |
| `action_policy` + `action_policy_spec` | What may happen unattended, and the exact allow / ask-first / never lists |
| policy keys | Every other string key is a standing rule: read it each tick and follow it |

Source kinds: `teams` (a channel: workspace_id, team_id, channel_id, max_results), `teams-chat`
(the owner's self-chat `48:notes`, `command_inbox: true`), `teams-dms` (the owner's 1:1 and group chats,
`addressed_only`), `slack` (a channel or the owner's self-DM, channel_id, limit), `slack-dms`
(addressed-only), `jira` (jql, limit, workspace_id), `monday` (boards, label, optional label_column, limit:
cards carrying the agent's label; read with the Monday MCP tools named in `_hub`, handled by the
`monday_tasks` / `monday_mentions` rules). Slack `@mentions` of the owner are not a source of their own: the
`slack_mentions` rule filters the messages the `slack` sources already read.

State — `~/.claude/channel-listener/state/<key>.json`: `{"last_seen": "...", "seen_ids": [...]}` (cap
`seen_ids` at ~200). Pending inbox — `state/pending.json`: in-scope items classified but not yet handled.
`state/handled.json`: message ids already answered (help, mentions, restarts).

## Tick protocol

0. **Re-read config.json EVERY tick and follow EVERY policy key in it** — the owner changes them while the
   loop runs. **A policy key only takes effect if it is listed here**, so this list must name every key the
   templates use: `fix_loop` (FIRST, before reading any source), `scope_only`, `post_format`,
   `message_format`, `alerts`, `dm_rules`, `chat_approvals`, `team_requests`, `jira`, `jira_tasks`,
   `test_recheck`, `knowledge_refresh`, `requirements_graph`, `two_readings`, `requirement_tracking`,
   `branch_rule`, `restart_command`, `help_command`, `slack_identity`, `teams_mentions`, `slack_mentions`,
   `slack_video_feedback`, `morning_digest`, `monday_tasks`, `monday_mentions`, `learning`,
   `action_policy_spec`, and `live_dashboard` (LAST step of the tick, builder only; a failed push is
   reported in one line and retried next tick — never block the tick on it). When a new key is added to a
   template, add it to this list in the same change.

For each source:

1. Read items newer than `last_seen`. **The APIs differ — do not treat them alike.**
   - **Slack** `slack_read_channel` takes `oldest` (epoch seconds): a real server-side since-filter. Page
     with the returned cursor until exhausted.
   - **Teams** `microsoft_list_channel_messages` has **no** since-parameter: it returns the newest N.
     Filter on `createdDateTime` client-side and watch for truncation — if the OLDEST message returned is
     still newer than `last_seen`, unread messages exist beyond the window: widen `max_results`, or say
     so in the tick report. Bodies are HTML: strip tags before matching. Author = `from.user.id`.
   - **Cap reads at ~5 messages per call.** Long-form posts run several KB each; large reads have errored
     out entirely (no data at all). Read 5, process, follow the cursor.
2. Drop ids already in `seen_ids`.
3. Self-filter: when `identities.teams.self_filter.mode` is `bot-prefix`, drop a self-authored message only
   if its body (tags stripped) starts with one of the prefixes (`[bot`). The agents post AS the owner, so
   filtering the owner's whole account would drop the owner's own requests.
4. **Stage 1 — regex prefilter.** A loose noise cut; it lets through more than it should on purpose.
5. **Stage 2 — relevance judgment** against `scope`: judge meaning, not keywords. **When genuinely unsure
   whether something is in scope, treat it as out of scope** — log it, take no action. Clearly in scope
   but the requirement is unclear → `action_policy_spec.unclear_requirement`.
6. **Commit to the inbox** (`pending.json`, `delivered: false`), persist it, *then* add the id to
   `seen_ids` and advance `last_seen`. Never advance the watermark before the inbox write is on disk.
7. Deliver and act on the inbox (one consolidated briefing, oldest first, urgent first).
8. Report one line per source: `<key>: N new, M in scope, K acted, P still pending`. An empty tick is one
   line, not a narrative.

### Command inbox — the owner's Teams self-chat (`teams-chat`, `command_inbox: true`)
How the owner drives the agents from a phone or browser without opening a workspace.
- A message starting with `[bot` is an agent's notice → skip. Any other message is **the owner** → a direct
  instruction; no keyword needed. Scope rules still apply.
- **Routing:** text starting with the tester's chat name is for the tester; everything else is for the
  builder. Each agent acts only on its own messages.
- **Reply** in the same chat, bot-marked (`post_format`): an ack first, then the result or next question.
- **Never actionable from chat:** secrets and merges. Deploys only through the approval tool
  (`chat_approvals`), which re-checks the sender, age and limits itself.
- Built-in words: `status`, `answer <ho-id> <text>`, `stop` / `start` (stop picking up new work),
  `deployed <ho-id>` (builder), plus `restart_command` and `help_command`.

### DMs (`teams-dms`, `slack-dms`, the owner's Slack self-DM)
Follow `dm_rules`: act only on messages that START with the agent's chat name (or an exact chat command),
from people in the organisation; skip everything else **without quoting, summarising or logging it**.
Reply on Teams; never post on Slack. Check the Slack connection's identity first (`slack_identity`).

## Action policy

| Value | Behaviour |
|---|---|
| `report-only` | Summarise in-scope items to the owner. No writes. |
| `investigate` | Also read-only lookups (tickets, cluster reads, repos). |
| `build-and-pr` | **Builder.** Build exactly to the tester's spec, unit tests, PR (never merge), hand-over report. No deploys outside an approval window, no merges, no Slack posts. Exact lists: `action_policy_spec`. |
| `spec-and-test` | **Tester.** Product owner + architect + tester: write specs (`handoff spec`), write and run tests, judge failures, report PASS/FAIL with the run id. Never edits product code, never deploys, never shares test content with the builder. |

Standing hard-stops regardless of setting: production deploys, merges, outbound posts the policy does not
allow, personal data, and any irreversible action stop for a human.

## Hard rules

- **Read-only on Slack.** A Slack post happens only when the owner explicitly asks for that post, and only
  after the session identity is re-checked that minute (`slack_identity`).
- **Filter out your own messages** (step 3), or a handler that posts where it reads retriggers forever.
- **An MCP timeout is not a failure.** Retrying a timed-out READ is safe; never retry a timed-out WRITE.
- **Dedup by message id, not timestamp** — edits change timestamps.
- **The listener dies with the session, the state does not.** The next session's first tick catches up
  (subject to the read-window check in step 1). Run `tick`, not `init`, on resume — `init` re-seeds to now
  and skips the gap.
- **Do not defer beyond the next tick.** An item stays pending only while its handler is genuinely
  incomplete.

## Stopping

Ctrl+C the loop, or ask to stop it. State persists in `~/.claude/channel-listener/state/`.
