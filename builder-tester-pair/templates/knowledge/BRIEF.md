## More than one line in production?
If the same app runs from more than one branch (e.g. one branch per cloud or per customer), list the other branch
under `knowledge.lines` in pair.yaml: it is pinned as `src/<app>-<line>`. Pages are written from the main line;
give every page an `applies-to:` line plus a section **"<other line> differs"** citing the other tree for every
behaviour that differs (or "none found in <files checked>"). Never describe one line's behaviour as another's.

## Hard rules
1. **Every factual sentence cites `repo/path/file.ext:LINE`** (or `:L1-L2`). No citation → it goes under
   "Open questions", never as fact. Quote short code fragments where they settle a point.
2. **Read code, not docs.** Docs, READMEs and agent notes may be stale; use them only as leads, and when a doc
   disagrees with the code, record it under "Doc drift" (doc path + code path).
3. **Never print or copy secret values.** For config: name the key, its source (env / secret / file) and its
   default; never a real value from a secrets file, `.env`, vault or secret manifest.
4. **Do not read the tester's scenarios** — never open {{never_read}}, or a checker's catalog. They are the holdout.
5. **Read-only.** No builds, no cluster commands, no network. Do not modify the source worktrees.
6. **Precision over coverage:** a smaller set of correct, cited pages beats a large vague one.
7. **Adversary gate before publishing:** an independent reviewer samples {{adversary_sample}} claims of every page against
   the code; a page with a wrong sampled claim is fixed and re-sampled before it is written to Engram ({{engram}}).
8. **`verified-at:` on every page** = the commit(s) it was checked against. The code wins whenever a page disagrees.

## How the library grows (the refresh rule)
- **Every merge:** `knowledge-refresh check` lists apps whose followed branch moved and the pages citing changed
  files. Each stale page is re-verified at the new commit (same rules, same adversary gate) and its `verified-at`
  updated; then `knowledge-refresh advance <app>`. Every NEW behaviour a merge adds (endpoint, rule, queue, config
  key, flow step) must land on a page — extend the right page or write a new one, linked to its requirement.
- **Every fixed bug** (a fix PR merged, or a bug ticket moved to Done) gets its own page of kind `bug`.
- **A test contradicts a page:** the tester runs `knowledge-refresh flag`; the builder re-verifies and closes the flag.
- **Every published page** is recorded: `knowledge-refresh record --page <area>/<file> --event new|updated|reverified|bug
  --sha <commit>` — it logs the change to the ledger and commits the library, so the knowledge has a full history.
- Which triggers are on is `knowledge.grow_on` in pair.yaml; which branch is followed is `knowledge.branch`.
